## 프롬프트 엔지니어링 프레임워크

### Phase 1: 요구사항 분석

```
분석 체크리스트:
□ 목표 출력 형태 (텍스트, JSON, 코드, 구조화)
□ 입력 데이터 특성
□ 일관성 요구 수준 (temperature)
□ 창의성 vs 정확성 비중
□ 토큰 예산
```

### Phase 2: 프롬프트 구조 설계

**표준 프롬프트 구조**:
```markdown
<system>
[Role Definition]
역할과 전문성 정의

[Capabilities]
할 수 있는 것과 없는 것

[Output Format]
기대하는 출력 형태

[Constraints]
제약 조건과 금지 사항
</system>

<user>
[Task Description]
수행할 작업 설명

[Context]
필요한 배경 정보

[Examples] (if few-shot)
입출력 예시

[Query]
실제 질문/요청
</user>
```

### Phase 3: 패턴 적용

| 패턴 | 사용 시점 | 구현 |
|------|----------|------|
| **Zero-shot** | 간단한 작업, 명확한 지시 | 예시 없이 직접 요청 |
| **Few-shot** | 특정 형식 필요, 복잡한 작업 | 2-5개 예시 포함 |
| **Chain-of-Thought** | 추론 필요, 복잡한 문제 | "단계별로 생각해보세요" |
| **Tree-of-Thought** | 다중 경로 탐색 필요 | 여러 접근법 동시 고려 |
| **ReAct** | 도구 사용 필요 | Thought-Action-Observation 루프 |

### Phase 4: 토큰 최적화

```
최적화 전략:
1. 불필요한 수식어 제거
2. 반복 표현 통합
3. 예시 압축 (핵심만)
4. 구조화된 형식 사용
5. 참조 대신 요약 사용
```

**토큰 예산 가이드**:
```
시스템 프롬프트: 최대 2000 토큰
사용자 프롬프트: 컨텍스트의 30% 이하
예시 (few-shot): 예시당 300-500 토큰
예약 (출력용): 최소 4000 토큰
```

## 모델 선택 가이드

### 작업별 추천 모델

| 작업 유형 | 추천 모델 | 이유 |
|----------|----------|------|
| 코드 생성/편집 | Claude Opus, GPT-4o | 정확성, 컨텍스트 이해 |
| 빠른 응답 | Claude Haiku, GPT-4o-mini | 속도, 비용 효율 |
| 창의적 작업 | Claude Sonnet | 창의성, 다양성 |
| 추론 집약 | OpenAI o3, Gemini 2.0 Pro | 깊은 추론 |
| 긴 컨텍스트 | Gemini 2.0, Claude | 큰 컨텍스트 윈도우 |

### 모델 파라미터 가이드

```yaml
temperature:
  0.0-0.3: 정확성, 일관성 중시 (코드, 분석)
  0.4-0.7: 균형 (일반 작업)
  0.8-1.0: 창의성 중시 (브레인스토밍)

max_tokens:
  짧은 응답: 500-1000
  중간 응답: 2000-4000
  긴 응답: 8000-16000
  
top_p:
  0.9: 기본값 (다양성과 일관성 균형)
  0.5: 더 집중된 응답
  1.0: 최대 다양성
```

## 프롬프트 품질 체크리스트

### 작성 후 검증
- [ ] 역할이 명확히 정의되었는가?
- [ ] 출력 형식이 구체적인가?
- [ ] 제약 조건이 명시되었는가?
- [ ] 애매한 표현이 없는가?
- [ ] 토큰 예산 내인가?

### 테스트 검증
- [ ] 기대 출력과 일치하는가?
- [ ] 엣지 케이스 처리되는가?
- [ ] 일관된 결과가 나오는가?
- [ ] 할루시네이션이 없는가?

## 고급 기법

### 컨텍스트 엔지니어링

```
정보 우선순위:
1. 가장 중요한 정보 → 프롬프트 시작과 끝에
2. 중간 중요도 → 중간에 배치
3. 참조용 → 필요시만 포함

압축 기법:
- 요약: 상세 문서 → 핵심 포인트
- 청킹: 긴 텍스트 → 관련 청크만
- 선택적 로딩: 필요한 부분만 로드
```

### 프롬프트 체이닝

```
복잡한 작업 분해:
Step 1: 분석 프롬프트 → 문제 이해
Step 2: 계획 프롬프트 → 접근법 결정
Step 3: 실행 프롬프트 → 작업 수행
Step 4: 검증 프롬프트 → 결과 확인
```

### 에러 핸들링

```
실패 복구 전략:
1. 프롬프트 재구성 (다른 표현)
2. few-shot 예시 추가
3. 단계 세분화
4. 모델 변경
5. 사용자 피드백 요청
```

## 사용 예시

### 예시 1: 시스템 프롬프트 최적화
```
요청: "이 에이전트 프롬프트를 최적화해줘"

분석:
- 현재 토큰: 5000
- 목표: 50% 감소
- 유지할 핵심: 역할, 제약, 출력 형식

결과:
- 중복 제거: -1000 토큰
- 예시 압축: -800 토큰
- 수식어 정리: -500 토큰
- 최종: 2700 토큰 (46% 감소)
```

### 예시 2: 모델 추천
```
요청: "코드 리뷰용 LLM 모델 추천해줘"

분석:
- 작업: 코드 분석, 버그 탐지
- 요구: 정확성, 상세 설명
- 예산: 중간

추천:
1순위: Claude Opus (정확성 최고)
2순위: GPT-4o (속도와 품질 균형)
3순위: Gemini 2.0 Pro (긴 파일 처리)
```
